# Investigation timeline

Reconstructed timeline of the analysis. Times are local.

| # | When | What happened |
|---|---|---|
| 1 | Aug 29, 22:13 | Started from an initial technical write-up of the incident: a `shahradr.exe` binary assumed to be packed with ~122.5 MB of `0x00` bytes in `.reloc`, an assumed RC4 cipher, and a direct `call rax` control transfer. Set out to build an isolated emulation environment to verify these claims independently and dynamically unpack the binary. |
| 2 | Aug 29, 22:13–22:27 | Environment recon: no passwordless `sudo` available, but a usable `rizin` binary was found bundled inside an already-mounted Cutter AppImage (`squashfs-root`) — avoided depending on any package install. |
| 3 | Aug 29, 22:27 | Reviewed a more detailed technical report of the (as it turned out, partially inaccurate) infection chain, with claimed server responses for each stage. |
| 4 | Aug 29, 22:27–23:03 | **Dynamic unpacking.** Set up a Python venv (`speakeasy-emulator`, `unicorn` 1.0.2, `capstone`, `pefile`, `lief`, `pycryptodome`), resolving version-compatibility issues along the way (`unicorn`/`distutils` under Python 3.13). Instrumenting CryptoAPI and memory operations disproved two assumptions from the initial write-up: the real cipher is AES-256-CBC (not RC4), and the `.reloc` "padding" isn't `0x00` but a low-entropy repeating pattern. Extracted the real key/IV, confirmed the Windows Thread Pool control-transfer mechanism, and dumped the unpacked buffer (573,600 bytes) to `payload_unpacked.exe`. |
| 5 | Aug 29, 23:03 | Continued toward reconstructing the final PE. Decompiled `fcn.140012470` and `fcn.140012230` with Ghidra (via `rz-ghidra`), confirming the memory-allocation logic and a conditional byte-reversal loop inside the binary itself. As an experiment, reversed the entire unpacked buffer byte-for-byte and got an incidental "MZ" (PE signature) match at offset 23224 — noted down to check properly. Work paused here for the day. |
| 6 | Aug 31 | Picked the investigation back up. Verified the infection chain independently by fetching the real stage URLs with `curl` directly against the live infrastructure, instead of relying on the original written report. This revealed the real per-victim stage tokens, the real archive password (**`10000`**, not `ShahradR_Pass2026` as originally assumed), the real dropper script content, and the exact infection-marker filename (`rx_unpack.ok`). Rebuilt this write-up around the verified findings, replacing the inaccurate parts of the original report. |
| 7 | Aug 31 | Went back and actually checked the offset-23224 lead from step 5 (see [`appendix/commands-log.md`](appendix/commands-log.md) for the exact command). **Result: it's another coincidence, same as an earlier unrelated "MZ" match** — the `e_lfanew` field right after that "MZ" points to an offset far outside the buffer, so it can't be a real PE header. Documented as a ruled-out lead in [`analysis/03-dynamic-unpacking.md`](analysis/03-dynamic-unpacking.md#byte-reversal-lead--checked-ruled-out). The real next step (finding where the offset-`0xD` pointer gets patched inside `fcn.140012470`) is still open — see [`analysis/04-payload-analysis.md`](analysis/04-payload-analysis.md).
